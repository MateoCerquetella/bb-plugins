## Security / correctness

The MCP tool boundary is correctly enforced in depth: the server exposes exactly four RPCs, SoulService.readTool and writeTool both reject any name outside ALLOWED_TOOLS before touching the client, and there is no generic tool-name RPC or storage/ticket/message code path. The only write is factory_soul_set, reachable solely from the app's save() which is gated on both confirmations (diff stage then exact-name plus acknowledgment), a non-empty trimmed author, and a non-empty edited soul; the server contract also validates bot/soul/author, so no unhandled path writes without confirmation. Credential hygiene is sound: the spawned factory child receives only a whitelisted runtime environment plus config overrides (not the full process.env), and startCommand redacts URL-embedded credentials. Post-save verification is honest: a successful write is only shown as 'Verified saved' after a matching souls/audit re-read, and any read failure or text mismatch degrades to a partial notice with the draft retained. No credential, token, or personal-data exposure was found.

## Design / maintainability

The plugin is cleanly layered (contract -> service -> mcp-client -> server, plus pure lib/soul and lib/draft helpers) and independently installable, with the deliberate MCP client/config duplication documented in D-001 as a boundary trade-off. Pure helpers keep diff, summary, audit, and verification logic unit-testable. The D-002 decision is faithfully implemented: the panel shows a not-reported tool state instead of inferring authority. Two minor maintainability notes are recorded as findings: the machine-specific default MCP path (F-2) and the absence of a committed unit-test/build receipt to substantiate the AC-11 'pass' claim (F-1); neither blocks shipping.
